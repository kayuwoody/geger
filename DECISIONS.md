# Decisions

One line per choice that SPEC.md didn't cover: what was decided, and why. Newest last.

- Phase 0 is a native Android app (Kotlin + ARCore) for the S22/S23 Ultra: the only test phones, full sensor and camera access, and ARCore results carry over to any final AR stack.
- QR plates put the code inside a black square frame: a QR code has finder patterns on only three corners, so the frame's four sharp corners drive the pose maths.
- M1: toolchain is Gradle 9.9.2, Android Gradle Plugin 9.5.1, Kotlin 2.4.21, JUnit 6.1.3 — the latest stable releases at the time; AGP 9 compiles Kotlin itself, so the app applies no separate Kotlin Android plugin.
- M1: compileSdk and targetSdk 37 — the Compose libraries in BOM 2026.09.00 require compiling against API 37, and the spec asks for the latest stable SDK; minSdk stays 29.
- M1: the Gradle project root is `android/` (matching the spec's repo layout); the `app` module is only included when an Android SDK is found, so the JVM modules and their tests build anywhere.
- M1: Java packages are `com.geger.positioning` (core), `com.geger.replay` (CLI) and `com.geger.trial` (app); application id `com.geger.trial`. Rename when the product has a name.
- M1: route cost = 3D length in metres, plus a 20 m lift penalty (config `display.liftPenaltyM`) standing in for waiting time; step-free routes skip stairs and escalators.
- M1: ARCore-world "heading 0" is defined as world −z, measured clockwise from above, so the ARCore→map alignment is just "heading + yaw"; at zero yaw ARCore −z maps to map +y.
- M1: the phone-heading rule's top-edge case uses ARCore's display-oriented camera pose (`camera.displayOrientedPose`), because the sensor-oriented `camera.pose` is landscape and its +y is not the screen's top edge in a portrait app.
- M1: map validation errors make a map unusable; geometry findings (nodes, plates, checkpoints outside walkable space, edges cutting through walls, unconnected nodes) are warnings so an imperfect survey doesn't block a test day. Lift edges must change level; stairs may stay on one level.
- M1: the config reader rejects unknown field names so a misspelt setting fails loudly instead of being ignored; map files ignore unknown fields so newer editors can add data.
- M2: the map editor is `index.html` plus two plain scripts (`map-core.js`, `editor.js`) in one folder — still no build step and opens from disk — so the validation logic can also be unit-tested under Node.
- M2: the editor re-implements map validation in JavaScript; shared fixtures in `maps/fixtures/` (ok-* load, bad-* rejected) are checked by both the Kotlin and the Node tests to keep the two in step.
- M2: map numbers must be real JSON numbers in both validators; the Kotlin loader previously accepted numbers written as text ("x": "1"), found by the shared fixtures and made strict.
- M2: export writes canonical JSON (fixed key order, one item per line, numbers rounded to 6 decimals, unknown fields kept at the end). "Version incremented on every save" is implemented as: the version goes up by one when a *changed* map is exported, so re-exporting an unchanged map gives a byte-identical file (the M2 check).
- M2: with Snap on, placed points snap to 0.1 m and dragged angles to 1°; exact surveyed values are typed in the Selection panel.
- M2: a loaded floor image gets a provisional background (origin at its bottom-left corner, 20 px/m) until Scale and Origin are set; the image file itself is not stored, only its name, scale and origin.
- M2: new plates and checkpoints get ids A01/C01 (zero-padded as in the spec's examples); nodes n1, levels L1, destinations D1.
- M3: `imu` and `rotation` records carry a stream field `s` ("a"/"g", "game"/"rot") instead of one combined record per sample, because the accelerometer and gyroscope (and the two rotation vectors) report separately with their own timestamps.
- M3: rotation quaternions are logged in ARCore's (x, y, z, w) order; Android's rotation-vector helper returns (w, x, y, z) and is reordered at the boundary.
- M3: `arcore_frame` records have `t` = receipt time on the elapsedRealtime clock and `ft` = ARCore's raw capture timestamp; ARCore doesn't document its clock, so the app measures it and writes a `timebase` record (base + offset) at session end. Frames also log `dq`, the display-oriented orientation, for the phone-heading rule.
- M3: added `timebase` records (one for the camera, one for the sensors) and a self-check screen after each recording: rates within 10% of target, zero drops, both clocks identified. `replay-cli check-session` re-runs the same checks on an exported zip and compares every stream's count with the phone's own totals.
- M3: ARCore uses the back camera at 30 fps with the largest CPU image available (for the M4 QR reader), BLOCKING update mode, autofocus, horizontal plane finding; no depth or light estimation.
- M3: the log is written uncompressed during the session (a crash leaves a readable file) and gzipped when the session stops; each session folder also keeps the exact config.json and map.json used.
- M3: a recording keeps running if the app leaves the screen (sensors continue); camera tracking stops and a note is logged. Requested sensor periods: 10 ms (IMU), 20 ms (rotation, magnetometer), 40 ms (barometer); Android treats these as hints.
- M3: the app is distributed as a debug APK installed from a file (docs/PHONE_SETUP.md); adb is optional, for crash logs.
- M4: the pose maths is plain Kotlin in positioning-core instead of OpenCV (`solvePnPGeneric`, `cornerSubPix`): it follows rule 3 (portable logic, runs in unit tests and the replay), and avoids a large native library in the app. Homography start + Levenberg–Marquardt refinement, both planar-ambiguity solutions kept.
- M4: frame corners are found by fitting straight lines to ~32 sub-pixel edge points per side, in two passes (the second re-scans around the first result). Edge points use the halfway-brightness crossing, not the steepest gradient: with bilinear interpolation the gradient is flat across each pixel, which gave ±0.5 px errors. Synthetic accuracy: under 0.35 px worst corner, 1.5–6 m.
- M4: QR orientation comes from the finder patterns (the corner without one is the code's bottom-right), not from the reader's corner order, so a plate is identified the same way however the reader orders its corners.
- M4: the final pose is solved with the plate held exactly vertical using ARCore's gravity (4 unknowns: turn about vertical + position). Gravity does not resolve the left/right mirror ambiguity, so both vertical solutions are solved; the better fit wins, and a fix is rejected when the mirror fits nearly as well (Δχ² < 16 at 0.5 px corner noise) yet puts the camera > 0.3 m (or 5% of the distance) away. That gate removed every wrong-mirror fix in the synthetic tests.
- M4: each fix carries its own uncertainty (covariance of the vertical solve propagated to map x, y, heading), combined with the config floor. Corner noise default 0.5 px.
- M4: the spec's synthetic check ("within 2% and 2° for 50 poses 1–10 m, up to 60°") is not physically achievable for distant head-on views, where heading is weakly observable from a 30–50 px square. The check became: accepted fixes measure distance within 2%; no accepted fix is badly wrong (> 25% / 15°); every accepted fix is within 3σ of its own reported uncertainty; ≥ 80% of accepted fixes seen ≥ 15° off head-on are within 2% / 2° (measured: 15/17 for 18 cm, 20/24 for 27 cm plates); ≥ 70% of views with a frame ≥ 60 px are accepted.
- M4: the QR reader is ML Kit Barcode Scanning (bundled model) on the ARCore CPU image's brightness plane, at up to 5 Hz on a worker thread; every sighting is logged (`qr_detection`) with reader corners, fitted corners, intrinsics, camera pose, both candidates and the result, so the replay can re-solve.
- M4: "QR calibration" run type ("Plates") with a frame-size field for plates not on a map; capture marks a spot (distance, angle chips) and logs the next 3 accepted fixes (10 s limit) as `calib_point`. The rotated-plate check is shown as the plate's in-plane rotation, and a sideways-mounted plate is rejected as not upright.
